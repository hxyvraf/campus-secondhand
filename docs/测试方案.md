# 校园二手交易平台 功能测试方案

## 一、测试策略

采用「**接口测试为主、界面功能测试为辅**」的策略，只做功能测试：

- **接口层**：用 Postman 集合覆盖 40 个接口的正常、异常、边界与权限场景，用 newman 批量执行，断言 HTTP 状态码 + 业务返回码 + 关键业务字段，作为主要执行证据；
- **界面层**：用浏览器真实点击主流程（登录、搜索、收藏、下单、发布、上下架、订单流转、消息、管理端），验证页面展示与交互反馈，并留截图；
- **数据层**：关键状态流转（订单状态、商品状态、收藏数、未读数）用 SQL 直接查库校验，确保接口返回与数据库一致。

## 二、测试范围与优先级

| 优先级 | 范围 | 说明 |
| --- | --- | --- |
| P0 | 注册登录、商品发布、商品搜索、下单与订单状态流转、收藏、消息未读数 | 主流程，必须 100% 执行 |
| P1 | 参数校验、权限控制、状态流转非法、重复提交、超时关闭、管理端功能 | 主要异常与风险场景 |
| P2 | 次要边界（超长文本、特殊字符）、排序方式、空状态、易用性提示 | 时间允许时执行 |

## 三、用例设计方法

| 方法 | 在本项目中的应用示例 |
| --- | --- |
| 等价类划分 | 价格：有效类 0.01–999999.99；无效类（负数、0、超上限、非数字）。商品状态：合法流转（在售→下架→上架）/ 非法流转（已下架商品再次下架） |
| 边界值分析 | 价格 0.01 / 999999.99 / 0.001 / 0 / 1000000；标题 1 / 50 / 51 字；分页 page=0 / 1 / 超总页数；size=0 / 1 / 100 / 101；文件 5MB 与 6MB |
| 场景法 | 主流程：注册→登录→发布→搜索→收藏→下单→卖家确认→买家完成→消息；分支流程：下单→取消 / 下单→超时关闭；异常流程：重复下单、购买自己的商品、越权操作 |
| 错误推测法 | 重复提交订单、重复收藏、并发下单、非法 token、被禁用账号、把 `id` 传成非数字、Content-Type 写错 |
| 状态迁移法 | 订单 5 个状态、商品 4 个状态的全部合法/非法迁移组合 |

## 五、接口测试规范

### 5.1 断言规范（每条用例必须包含）

1. **HTTP 状态码断言**：200/400/401/403/404/405/409/415/500 之一；
2. **业务返回码断言**：与状态码配合（如 400 ↔ 40001、409 ↔ 40901），验证双层返回一致；
3. **字段级断言**：类型与取值校验，例如 `body.data.token` 为长度大于 20 的字符串、`body.data.status === 'PENDING_CONFIRM'`；
4. **业务规则断言**：例如商品被下单后 `status` 变为 `LOCKED`、取消订单后商品回到 `ON_SALE`、分页 `size=100` 时返回 100 条。

### 5.2 变量管理

Postman 环境变量统一放在 `campus-trade.postman_environment.json`：

| 变量 | 写入位置 | 用途 |
| --- | --- | --- |
| `baseUrl` | 环境文件 | 接口根地址 |
| `buyerToken` / `sellerToken` / `seller2Token` / `adminToken` | 各登录用例 | 各角色鉴权 |
| `productId` / `minPriceProductId` / `maxPriceProductId` | 发布商品用例 | 下单、收藏、上下架等后续用例 |
| `orderId` / `cancelOrderId` / `cancelProductId` | 下单用例 | 订单状态流转用例 |
| `newUsername` / `newUserId` / `newUserToken` | 注册与登录用例 | 禁用/启用等用户状态用例 |
| `categoryId` | 新增分类用例 | 修改、删除分类用例 |

### 5.3 执行方式

```bash
# 在项目根目录执行（上传用例依赖相对路径的测试素材）
newman run docs/postman/campus-trade.postman_collection.json \
  -e docs/postman/campus-trade.postman_environment.json \
  -r cli,htmlextra,json \
  --reporter-htmlextra-export docs/测试执行证据/newman-report.html
```

Windows 下可直接双击 `跑接口测试-newman.bat`。

## 六、测试数据准备

### 6.1 初始数据

后端首次启动自动创建数据库并写入初始数据（`backend/src/main/resources/db/schema.sql` 与 `data.sql`），包括 6 个分类、4 个测试账号、20 件商品（覆盖全部商品状态）、3 条收藏、2 笔订单、4 条站内消息。

### 6.2 造数脚本（常用）

```sql
-- 1) 把某条待确认订单改成"已超时"，用于验证超时自动关闭
USE campus_trade;
UPDATE trade_order
SET expire_at = DATE_SUB(NOW(), INTERVAL 5 MINUTE)
WHERE id = 1 AND status = 'PENDING_CONFIRM';

-- 2) 验证完超时后恢复数据（或直接双击「重置数据.bat」）

-- 3) 批量造商品，用于测试分页与搜索（可与接口测试账号配合）
INSERT INTO product (seller_id, category_id, title, description, price, condition_level, trade_place, status)
SELECT 2, 1, CONCAT('批量测试商品-', n.id), '分页测试数据', 10 + n.id, '九成新', '图书馆一楼', 'ON_SALE'
FROM (SELECT 1 id UNION SELECT 2 UNION SELECT 3 UNION SELECT 4 UNION SELECT 5) n;

-- 4) 校验订单与商品状态是否联动正确
SELECT o.id, o.status AS order_status, p.status AS product_status
FROM trade_order o JOIN product p ON p.id = o.product_id
ORDER BY o.id DESC LIMIT 10;

-- 5) 校验收藏数与收藏表是否一致
SELECT p.id, p.favorite_count, (SELECT COUNT(*) FROM favorite f WHERE f.product_id = p.id) AS real_count
FROM product p WHERE p.favorite_count > 0;

-- 6) 校验未读消息数
SELECT user_id, COUNT(*) AS unread FROM message WHERE is_read = 0 GROUP BY user_id;
```

## 七、执行流程

1. **冒烟测试**：登录、商品列表、商品详情、下单、消息未读数 5 条主链路，确认环境可用；不通过则打回开发（不进入详细测试）；
2. **接口功能测试**：newman 整体执行 Postman 集合（162 个请求），失败用例定位后提交缺陷；
3. **界面功能测试**：浏览器按用例步骤执行，重点验证提示文案、状态标签、跳转与列表刷新；
4. **数据校验**：对订单/商品状态、收藏数、未读数执行 SQL 交叉校验；
5. **回归测试**：缺陷修复后执行对应用例 + 集合整体回归，确认无副作用；
6. **测试总结**：统计用例执行情况与缺陷分布，输出测试报告。

## 八、缺陷管理流程

### 8.1 状态流转

`新建 → 处理中 → 已解决 → 已验证 → 已关闭`，未通过验证时退回 `处理中`（重开）。每次修复后必须记录回归版本与回归结论。

### 8.2 严重程度定义

| 严重程度 | 判定标准 | 示例 |
| --- | --- | --- |
| 严重 | 主流程不可用、数据错误或丢失、越权可操作他人数据 | 重复提交生成重复订单、买家能确认卖家才该确认的操作 |
| 中 | 功能受限但有替代路径、返回码/提示信息错误、边界未校验 | 参数越界未拦截、业务码不准确、Content-Type 错误返回 500 |
| 轻微 | 文案、样式、排序等不影响功能的问题 | 提示语不通顺、空状态文案缺失 |

### 8.3 缺陷编写要求

必须包含：标题（条件+操作+现象）、环境与版本、前置数据、最小复现步骤、预期结果、实际结果（附状态码/业务码/截图或报告路径）、严重程度与优先级。

## 九、通过标准

1. 接口集合整体执行通过（446 条断言全部通过），HTML 报告归档；
2. P0/P1 用例执行率 100%，通过率 ≥ 95%；
3. 严重及以上缺陷修复率 100%，回归通过；
4. 关键业务规则（订单状态机、商品状态联动、重复提交防护、权限控制、超时关闭）均有对应用例与证据。

## 十、风险与规避

| 风险 | 规避方式 |
| --- | --- |
| 用例间强依赖导致顺序执行失败 | 明确执行顺序，使用环境变量串联；失败时先跑前置文件夹 |
| 定时任务超时场景耗时长 | 用 SQL 造数 + 管理端手动扫描接口，秒级验证 |
| 测试数据被污染 | 使用「重置数据.bat」恢复；用例断言使用相对判断 |
| 前端手工用例漏执行 | 用例表标注执行状态，未执行项在报告中列明并列为遗留问题 |
