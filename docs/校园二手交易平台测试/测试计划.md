# 校园二手交易平台 功能测试计划

> **本计划只讲功能测试**：在浏览器上按真实用户的操作方式，验证各模块功能是否符合需求。
> 不包含接口测试，也不包含性能、安全、兼容性等非功能测试（接口测试单独进行，不在本计划内）。
>
> 配套文档：[测试点梳理.md](测试点梳理.md)（144 个测试点）、[测试用例.xlsx](测试用例.xlsx)（功能测试用例，编号 TC-FE-xxx）、
> [测试报告.md](测试报告.md)（执行结果）、[缺陷记录表.xlsx](缺陷记录表.xlsx)。

## 一、测试目标

| 编号 | 目标 | 判定方式 |
| --- | --- | --- |
| G1 | 各模块功能符合第三节「需求基线」 | 各模块 P0 用例 100% 执行且通过 |
| G2 | 主流程可以完整走通：注册 → 登录 → 发布 → 搜索 → 收藏 → 下单 → 卖家确认 → 买家完成 → 消息可见 | 端到端流程用例通过 |
| G3 | 业务规则正确：商品状态、订单状态、收藏数、未读数 | 状态类用例全部通过，并用 SQL 交叉校验数据一致 |
| G4 | 输入校验与提示准确：必填、长度、格式、数值范围 | 每条校验都有明确提示且阻止提交 |
| G5 | 权限控制正确：未登录跳登录、越权被拦截、被禁用账号不可用 | 权限类用例全部通过 |

### 3.4 搜索与收藏（REQ-SEARCH / REQ-LIST / REQ-DETAIL / REQ-FAV）

搜索模块按《功能-搜索需求》的样式描述：**需求 | 用户（输入/操作） | 系统（返回/行为）**，分「输入、匹配、排序」三组。

#### 3.4.1 搜索需求

**1、输入**

| 需求 | 用户 | 系统 |
| --- | --- | --- |
| 关键词搜索 | `教材`、`鼠标`、`数据结构` | 命中标题或描述包含关键词的在售商品 |
| 英文不区分大小写 | `java`、`JAVA` | 都能命中《Java 程序设计》第 3 版 |
| 前后空格忽略 | ` java ` | 与 `java` 结果一致 |
| 无结果 | `不存在的商品关键词xyz` | 展示空状态「没有找到符合条件的商品」，页面不报错 |
| 特殊字符输入 | `%`、`_`、单引号 | 页面不报错、不返回异常数据（`%` 目前会被当成通配符，见 3.4.4 待确认项） |

**2、匹配**

| 需求 | 用户 | 系统 |
| --- | --- | --- |
| 分类筛选 | 点击「数码电子」 | 只展示该分类商品，标签高亮 |
| 价格区间 | 拖动价格滑块到 20-60 | 只展示价格落在区间内的商品 |
| 组合筛选 | 关键词 + 分类 + 价格区间 | 三个条件同时生效 |
| 重置筛选 | 点「重置」 | 关键词、分类、价格、排序全部恢复默认 |
| 匹配为空 | 筛选后没有结果 | 展示空状态提示，不出现空白页或报错 |

**3、排序**

| 需求 | 用户 | 系统 |
| --- | --- | --- |
| 最新发布（默认） | 不选择排序 | 按发布时间倒序展示 |
| 价格排序 | 选择「价格从低到高 / 价格从高到低」 | 列表按价格升序 / 降序 |
| 收藏最多 | 选择「收藏最多」 | 按收藏数降序展示 |

| 当前状态 | 操作 | 操作后状态 | 操作人 | 附加效果 |

## 七、测试数据准备

初始数据由后端启动时自动写入，正常不需要手工造数。功能测试特有的 4 个数据动作：

```sql
USE campus_trade;

-- 1) 超时关闭场景：把待卖家确认订单的确认期限改成过去时间，再让管理员「触发订单超时扫描」
UPDATE trade_order SET expire_at = DATE_SUB(NOW(), INTERVAL 5 MINUTE)
WHERE id = 1 AND status = 'PENDING_CONFIRM';

-- 2) 分页与搜索场景：批量造 5 件在售商品
INSERT INTO product (seller_id, category_id, title, description, price, condition_level, trade_place, status)
SELECT 2, 1, CONCAT('分页测试商品-', n.id), '分页测试数据', 10 + n.id, '九成新', '图书馆一楼', 'ON_SALE'
FROM (SELECT 1 id UNION SELECT 2 UNION SELECT 3 UNION SELECT 4 UNION SELECT 5) n;

-- 3) 收藏数与收藏记录一致性校验（正常应查不到记录）
SELECT p.id FROM product p
WHERE p.favorite_count <> (SELECT COUNT(*) FROM favorite f WHERE f.product_id = p.id);

-- 4) 未读数校验（与页面红点数量对比）
SELECT user_id, COUNT(*) AS unread FROM message WHERE is_read = 0 GROUP BY user_id;
```

数据规则：**每轮测试前先执行「重置数据.bat」**；测试中产生的商品、订单保留作为证据；如果检查结果受历史数据影响，
改成相对判断（例如"至少 1 件"）或先重置再测。

## 十一、缺陷处理

- 判定：功能与第三节需求不一致、状态流转错误、数据不一致、提示文案错误，都记为功能缺陷；
- 严重程度：**严重**（主流程不可用、数据错误、能看到或操作到不该操作的数据）、**中**（功能受限或提示错误）、**轻微**（文案与样式）；
- 流程：新建 → 处理中 → 已解决 → 已验证 → 已关闭；修复后必须回归对应用例与端到端主流程；
- 记录：写入[缺陷记录表.xlsx](缺陷记录表.xlsx)，必须包含复现步骤、预期、实际、修复说明与回归结果。

## 十三、风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 历史数据累积（上轮产生的订单、商品、收藏） | 列表数量、收藏数等检查结果失真 | 每轮开始先「重置数据.bat」；检查时用相对判断 |
| 状态没恢复（商品被下架、订单没取消） | 影响后续用例 | 一轮结束后重置数据；用例之间避免依赖同一件商品 |
| 超时关闭需要等 30 分钟 | 用例执行周期长 | 用第七节 SQL 把 `expire_at` 改到过去时间，或让管理员点「触发订单超时扫描」 |
| 需要多个账号来回切换 | 容易漏步骤或串号 | 按「买家 buyer01 → 卖家 seller01 → 管理员 admin」顺序执行，退出登录后再切账号 |
| 手工用例容易被跳过 | 覆盖不完整 | 用例表必须回填执行状态；报告中的「遗留问题」列出未执行项 |
