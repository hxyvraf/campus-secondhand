### 2.2 本轮不做

性能测试（并发下单、响应时间、定时任务多实例幂等）、安全专项（SQL 注入、XSS、越权组合矩阵、令牌吊销策略）、
兼容性专项（多浏览器/多分辨率矩阵）、非功能项（可用性、可维护性、备份恢复）、以及系统未实现的能力
（支付、短信/邮件、图片云存储）。这些内容在本轮只做一句话记录，不设计用例、不排期。

## 三、测试项与测试内容（功能测试重点）

### 3.1 注册登录（TC-IF-001~025 / TC-FE-001~009）

| 功能项 | 要验证的功能行为 |
| --- | --- |
| 注册 | 用户名规则（4-20 位字母数字下划线，边界 3/4/20/21）、密码规则（6-20 位）、昵称必填、手机号与邮箱格式、用户名重复被拦截、响应不含密码、密码 BCrypt 入库 |
| 登录 | 正确账号可登录并拿到 token；密码错误/账号不存在均返回 401/40102 且提示不泄露账号是否存在；空用户名、空密码返回 400 |
| 鉴权 | 未带 token、token 非法、token 过期均 401/40101；白名单接口匿名可用；`/api/products/mine` 不被白名单误放行；被禁用账号即使有 token 也拒绝（403/40302） |
| 修改密码 | 原密码错误、新旧密码相同、新密码过短均被拦截；改完后旧密码不可登录 |
| 退出 | 接口返回成功，前端清除本地 token 并跳转登录页 |

| 更新资料 | 昵称/手机号/邮箱/学校/头像可更新；手机号格式、昵称长度越界被拦截；未登录 401 |

## 六、功能测试数据准备

初始数据由后端启动时自动写入，不需要手工造数；下面 4 条是本轮功能测试特有的造数动作：

```sql
USE campus_trade;

-- 1) 超时关闭场景：把待卖家确认订单的确认期限改成过去时间，再调管理端超时扫描接口
UPDATE trade_order SET expire_at = DATE_SUB(NOW(), INTERVAL 5 MINUTE)
WHERE id = 1 AND status = 'PENDING_CONFIRM';

-- 2) 分页/搜索场景：批量造 5 件在售商品
INSERT INTO product (seller_id, category_id, title, description, price, condition_level, trade_place, status)
SELECT 2, 1, CONCAT('分页测试商品-', n.id), '分页测试数据', 10 + n.id, '九成新', '图书馆一楼', 'ON_SALE'
FROM (SELECT 1 id UNION SELECT 2 UNION SELECT 3 UNION SELECT 4 UNION SELECT 5) n;

-- 3) 收藏数与收藏表一致性校验（应无结果）
SELECT p.id FROM product p
WHERE p.favorite_count <> (SELECT COUNT(*) FROM favorite f WHERE f.product_id = p.id);

-- 4) 未读数校验
SELECT user_id, COUNT(*) AS unread FROM message WHERE is_read = 0 GROUP BY user_id;
```

数据隔离规则：**每一轮功能测试开始前都先执行「重置数据.bat」**；测试中产生的订单、商品不做删除（作为证据保留），
发现断言受历史数据影响时，改用相对判断（例如"不小于 1 件"）或先重置再跑。

**准入**：后端可启动且数据库初始数据完整；40 个接口在 Swagger 中可见；主流程可手工走通；测试账号可用。

**准出**：

1. P0 用例执行率 100%、通过率 100%；P1 用例执行率 100%、通过率 ≥ 95%；
2. 接口功能测试整体执行通过（162 请求 / 446 断言 0 失败）；
3. 端到端流程（下单→卖家确认→买家完成）与 3 条分支流程（取消、超时、重复提交拦截）全部通过；
4. 严重与中等缺陷修复率 100% 且回归通过，无遗留严重缺陷；
5. 状态与数据一致性 SQL 校验无异常结果；
6. `测试用例.xlsx` 中每条已执行用例都填了实际结果，未执行的用例在测试报告中明确列为遗留项。

## 十、缺陷处理（功能缺陷）

- 判定：功能与需求/接口文档不一致、状态流转错误、数据不一致、提示或返回码错误，均记为功能缺陷；
- 严重程度：**严重**（主流程不可用、数据错误、越权可操作他人数据）、**中**（功能受限或返回码/提示错误）、**轻微**（文案与样式）；
- 流程：新建 → 处理中 → 已解决 → 已验证 → 已关闭，修复后必须回归对应用例 + 全量接口集合；
- 记录：写入[缺陷记录表.xlsx](缺陷记录表.xlsx)，必须包含复现步骤、预期、实际（含状态码/业务码）、修复与回归结果。

## 十二、功能测试风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 用例之间有数据依赖（token、商品 ID、订单 ID） | 打乱顺序执行会失败 | 集合内按分组顺序整体执行；每次跑前先重置数据 |
| 历史数据累积（上轮产生的订单/商品） | 断言结果失真 | 每轮开始先「重置数据.bat」；断言使用相对判断 |
| 超时关闭场景需要等待 30 分钟 | 用例执行周期长 | 用第六节的 SQL 把 `expire_at` 改到过去时间 + 管理端手动触发扫描 |
| 前端手工用例容易被跳过 | 覆盖不完整 | 用例表必须回填执行状态；报告的「遗留问题」列出未执行项 |
| 状态未恢复（例如商品被下架、订单未取消） | 影响后续用例 | 结束一轮后执行「重置数据.bat」恢复现场 |
